## 개발 현황 업데이트 — 기록 기준일: 2026-10-18

> **기존 문서의 86개 테스트/MVP 설명은 10월 17일 당시의 기록이다.** 아래는 10월 18일까지 Codex가 보고한 구현·검증 내역이며, 저장소를 여기서 직접 재검사한 것은 아니다.

### 현재 프로젝트 범위

- **GYUVIS와 GyuNexus Core**: 자연어 대화, 기억, 상황 기반 선제 제안, 근거 중심의 Research·Idea·Developer·Critic 토론을 지향한다. 채택/추가 조사/폐기와 근거·비용·승인 제어를 유지한다.
- **AI 직원(Workers)**: 직원별 역할·모델·허용 도구·업무 템플릿·실행·결과물·승인·작업 공간을 관리한다. 뉴스 리서처와 블로그 포스팅 담당을 실제 등록하여 검증했다.
- **워크플로(Worker Orchestration)**: 자연어 목표를 작업 DAG로 계획하고 기존 Worker 실행 엔진으로 여러 직원에게 분배한다. 선행 결과물은 Artifact ID·버전·SHA-256으로 자동 전달하고, 승인 전 후속 업무를 시작하지 않는다.
- **웹 UI**: 직원, 실행 이력, Markdown 결과물 미리보기/원본 전환, 승인, 워크플로 계획·수정·실행·상태·비용·결과물 계보를 지원한다.

### 뉴스 조사 직원과 블로그 작성 직원

- 뉴스 수집 도구: `news.search`, `rss.fetch`, `web.fetch`. 원문 확인 여부, 출처 URL, 게시일, 수집 시각, 검증 수준을 표시한다.
- 뉴스 보고서는 필수 섹션을 서버가 조립하며, 구조적 완료 기준(기사별 필수 필드, 제목 후보, 추가 확인 사항, 중복 여부, 형식)은 코드로 검사한다. 의미적 적절성처럼 구조로 판단하기 어려운 기준은 LLM 검수에 남긴다.
- 사용자 화면에서 뉴스 조사 실행 #4는 수집 후보 63건 중 5건을 선정하고 **첫 시도 검증 통과 → 승인 대기**까지 진행했다. API 호출 3회, 약 \$0.00379. 해당 실행의 5건은 '검색·피드 결과만(미검증)' 표기였고, 사용자는 출처 링크가 실제 기사와 맞는다고 직접 확인했다. 링크 일치와 요약 전체의 사실 검증은 별개이다.
- Markdown `.md` 결과물은 React 기반 안전한 미리보기(제목·목록·링크 등)와 원본 전환/복사를 제공한다. `http(s)` 링크만 열고 HTML을 실행하지 않는다. 표 지원과 승인 화면의 300자 미리보기 제한은 남아 있다.
- 블로그 담당은 고정된 목차보다 사용자의 실제 기술 블로그 문체·흐름을 따르는 방향으로 지시한다. 단독 실행 시 자료가 없는 경우 `needs_input`으로 종료한 사례가 있다. 반면 워크플로 단계로 실행할 때는 승인된 선행 Artifact를 자동 참조한다.

### 다중 직원 워크플로 구현·검증

- 직원·업무 카탈로그를 읽는 LLM 플래너가 DAG를 제안하고, 서버가 존재 여부·직원-업무 소속·권한·의존성 순환·예산을 검증한다. 실행 전 계획 확인이 기본값이며 자동 실행은 명시적 동의가 필요하다.
- 독립 작업은 병렬 실행(기본 최대 3개), 승인 대기 단계에서 중단, 실패 단계 재시도, 일시정지·재개·취소, 재시작 후 상태 복구를 지원한다.
- 결과물은 경로 복사 대신 버전·해시 고정 참조로 전달되고, 조회 시 해시를 재확인한다. 여러 선행 결과물 입력과 계보 조회를 지원한다.
- 테스트 전용 DB와 실제 OpenAI·뉴스 소스로 **뉴스 조사 → 중간 승인 → 블로그 초안 → 최종 승인 → completed** 전체 경로를 확인했다. 보고된 총 비용은 약 \$0.0047이다. 이는 테스트 환경 결과이며 사용자 DB에서의 장기 운영 검증을 뜻하지 않는다.

### 예산 관리 및 최근 버그 수정

- 워크플로 총예산은 생성 후에도 계획 수정 또는 별도 '예산 변경' 창에서 조정할 수 있다(0 USD 초과, 최대 5 USD). 실행 전·진행 중·승인 대기·일시정지·실패 상태에서 허용하고 완료·취소에서는 제한한다.
- 최소 허용 예산은 **이미 사용한 금액 + 미완료 단계의 남은 비용 상한**을 기준으로 검증한다. 변경 이력과 당시 사용액을 기록하며, 증액 후 실행 가능한 단계는 재개한다.
- 계획에서 실행 이력이 있는 단계를 제거해도 비용과 계보가 사라지지 않도록 `WorkerRun.workflow_id` 중심으로 누적 사용액을 집계한다. 실행된 단계는 삭제 대신 `removed`로 보존해 SQLite 단계 ID 재사용 문제도 방어했다.
- 기존 데이터의 누락된 `workflow_id`는 가능한 경우 서버 시작 시 `slot_key`로 복원한다. 이전에 삭제된 단계와 `slot_key`가 모두 없는 실행의 비용은 복원 불가할 수 있다.
- **계획 생성 실패 복구 수정 보고(10월 18일):** 예산 부족으로 계획 생성이 실패할 때 `plan_state`, `plan_error_kind`, `plan_error_budget_usd`, `proposed_steps` 등 구조화된 정보를 보존한다. 예산만 부족하고 제안이 남아 있으면 증액 시 LLM 호출 없이 재검증해 단계를 복구한다. 오래된 실패 워크플로는 `POST /api/workflows/{id}/replan` 또는 화면의 '현재 예산으로 AI가 계획 다시 생성'으로 새 계획을 생성한다. 실패 이력은 `workflow_plan_attempts`에 유지한다. 과거 예산 \$0.50 오류가 현재 상태처럼 남는 문제와 `validate_plan`의 `wid` 변수 덮어쓰기 문제도 수정했다고 보고됐다. 기존 사용자 DB에는 아직 적용·검증하지 않았으며 서버 재시작 후 과거 워크플로의 수동 재생성이 필요하다.

### 최신 테스트와 운영 주의

- Codex 보고 기준 **백엔드 238개 테스트 통과**, 프런트 타입체크·빌드 통과. 테스트 수 증가: 193(뉴스 도구) → 198(섹션) → 202(완료 기준) → 222(워크플로) → 232(예산 편집) → 238(누적 비용 수정).
- 실제 외부 서비스/OpenAI 테스트는 임시 DB에서 수행했으며 사용자 DB·결과물은 삭제하거나 초기화하지 않았다고 보고됐다.
- **서버 재시작 필요**, 새 컬럼 및 기존 데이터 보정 적용 여부 확인 필요. 변경분은 보고 당시 Git에 커밋되지 않았다.
- 남은 제약: 단일 서버 프로세스 락 가정, 후속 입력 총 30,000자 제한, 중복 사건의 오탐·미탐, 플래너 품질의 LLM 의존성, 승인 화면의 잘린 미리보기, 계획 생성 실패 후 예산 증액 복구.
- 다음 우선순위: (1) 서버 재시작 및 구버전 실패 워크플로 수동 재생성 후 실제 실행 확인, (2) 사용자 환경의 누적 비용·승인·이력 점검, (3) GYUVIS 채팅에서 워크플로 계획·실행으로 이어지는 연결 여부 확인.

# GyuNexus 프로젝트 문서

> 
**GyuNexus는 사용자 맥락을 이해하는 개인 AI 비서의 Core이며, GYUVIS가 자연스러운 대화·기억·선제 제안을 맡고 GyuNexus가 근거 중심의 자율 멀티에이전트 토론을 담당한다.**

## 1. 프로젝트 정체성

GyuNexus의 목표는 “명령을 잘 수행하는 챗봇”이 아니라, 사용자의 상황과 기록을 연결해 필요한 순간에 먼저 제안하는 개인 AI 비서다.

- **GYUVIS**: 사용자가 대화하는 인터페이스. 자연스러운 대화, 개인 기억의 활용, 상황에 맞는 선제 제안을 지향한다.
- **GyuNexus**: 기억·상태·도구·에이전트·자동화를 연결하는 Core. 주제를 스스로 발굴하고, 여러 역할의 에이전트가 토론·검증해 유용한 제안을 만든다.
- **행동 원칙**: 관찰(Observe) → 판단(Decide) → 제안·승인(Ask) → 실행(Act) → 보고(Report) → 기억(Memory). 위험하거나 중요한 행동은 사용자의 승인을 전제로 한다.

이 프로젝트는 모든 결정을 AI에 위임하려는 것이 아니다. 단순하고 명확한 판단은 규칙으로 처리하고, 요약·추론·의미 중복 판정처럼 모델이 필요한 지점에만 LLM을 사용한다.

## 2. 현재 MVP

현재 MVP는 개인 기억과 상태를 바탕으로 주제를 만들고, 역할별 에이전트가 토론한 결과를 저장·분류하여 GYUVIS에 전달할 수 있는 파이프라인이다.

```txt
사용자 대화 · 기억 · 상태 · 도구 결과
                ↓
      GyuNexus 주제 발굴 / 계획
                ↓
Research · Idea · Developer · Critic
                ↓
증거 검증 · 종합 · 상태 분류
                ↓
채택된 제안만 GYUVIS에 전달
                ↓
결과와 맥락을 Memory에 축적
```

### 구현된 흐름

- 적게 다룬 기억을 중심으로 자율 토론 주제를 발굴한다.
- 주제 성격에 따라 참가자를 정한다. 최신 사실·수치·조사가 필요하면 **Research**, 소프트웨어 주제면 **Developer**, **Critic**은 항상 참여한다. 선택·제외 이유는 계획과 활동 로그에 남긴다.
- Research의 도구 조회 결과와 실패는 모두 증거로 기록한다. 강수확률, 구름량, 달 밝기처럼 결론에 영향을 주는 경고도 프롬프트·종합·최종 결과까지 전달한다.
- 주장은 사실·해석·추정·제안으로 분류한다. `verified`는 인용된 증거에 실제로 있는 수치·사실에만 붙인다.
- Critic은 오류, 누락 조건, 증거 모순, 반례, 실행 위험 중 하나를 근거로 대상 문장을 인용하고 대안을 제시해야 한다. 형식적·중복·근거 없는 반박은 재작성 대상이다.
- 아이디어는 `accepted`, `needs_research`, `discarded`로 분류한다. 기본 아이디어 목록과 GYUVIS 추천에는 채택된 아이디어만 포함한다.
- 증거 경고와 모순되거나 핵심 고유명사의 존재가 확인되지 않은 제안은 채택하지 않고 추가 조사가 필요함을 표시한다.

## 3. 검증 현황

> 
이 MVP는 품질 평가를 계속하는 단계다. 파이프라인과 주요 안전 규칙은 검증했지만, 자율 협업이 지속적으로 좋은 판단을 낸다는 결론에는 아직 이르지 않았다.

- 백엔드 테스트 **86개 통과**: 기존 47개와 신규 39개.
- 프런트엔드 빌드 통과.
- 실제 OpenAI **gpt-4o-mini** 호출과 임시 DB로 검증했다. 사용자 실제 DB에는 쓰지 않았다.
- 실제 재실행에서 이전의 핵심 문제였던 Research 누락, 형식적 반박, 증거 경고 무시는 재현되지 않았다.
- 테스트로 확인한 항목: Research 필수/생략, 증거와 충돌하는 결론 거부, 근거 없는 고유명사 차단, 내용 없는 Critic 반박 거부, 타당한 주장 보존, 반복 반박 시 정체 종료, 폐기 아이디어 추천 차단, 도구 오류·경고 전달, 토큰·예산 상한.
- 새 UI·음성·HUD·PC 제어 기능은 이번 범위에 추가하지 않았다. 기존 화면에는 채택·추가 조사 필요·폐기 같은 상태 라벨만 맞췄다.

### 실제 호출에서 확인한 개선

- 날짜와 장소처럼 조사할 정보가 있는 주제에는 Research가 선택되고, 개발 주제에서는 제외 사유가 남는다.
- 높은 구름량·달 밝기 같은 경고가 최종 결론과 전달 메시지에 반영된다.
- Critic은 누락 조건이나 실행 위험을 지적하는 구체적 반박을 만들었고, 중복 반박은 재작성되었다.
- 잘못된 날짜 도구 호출은 현재 날짜와 “이번 주말”의 실제 날짜를 프롬프트에 제공하도록 보완했다.

## 4. 아키텍처

```txt
GYUVIS
  ├─ 자연스러운 대화
  ├─ Memory 활용
  └─ 선제 제안의 표시·전달
          ↑
GyuNexus Core
  ├─ Memory / 개인 맥락
  ├─ Topic Discovery
  ├─ Debate Planner
  ├─ Research · Idea · Developer · Critic
  ├─ Evidence / Warning 검증
  ├─ Synthesis / Idea 분류
  ├─ Budget · Token · 종료 제어
  └─ 승인 기반 Automation 연계
          ↑
도구 · 일정 · PC 상태 · 센서 · 외부 데이터
```

토론은 매 라운드에서 새 증거, 새 반박, 반박 처리, 보존해야 할 검증 내용을 추적한다. 종료 사유는 합의, 추가 조사 필요, 정체, 최대 라운드, 토큰·일일 예산으로 구분한다. 사실 확인이 필요한 주제는 검증된 사실 없이 합의로 끝나지 않도록 한다.

## 5. 기술 스택과 구현 경계

- **백엔드 / Core**: Python, FastAPI, 데이터베이스, 에이전트·메모리·자동화 로직
- **LLM 검증 모델**: gpt-4o-mini
- **사용자 인터페이스**: 웹 UI와 GYUVIS 대화 흐름
- **데이터·안전장치**: 증거 레코드, 경고 전파, 아이디어 상태, 토큰·일일 예산, 승인 기반 실행
- **운영 호환성**: 기존 DB에 필요한 새 컬럼을 시작 시 추가할 수 있게 했으며, 호환성 검증은 임시 구버전 DB에서만 수행했다.

Core는 장기적으로 OS나 기기별 구현과 분리한다. GyuNexus는 공통 맥락·판단·메모리를 맡고, PC 제어·센서·OS 고유 자동화는 환경별 Agent가 capability에 맞춰 제공하는 방향이다.

## 6. 아직 미구현이거나 위험한 부분

- 실제 LLM 환경에서 **합의 종료**와 **정체 종료**는 충분히 재현하지 못했다. 현재 실제 실행은 최대 라운드 종료가 많았다.
- Critic이 증거 모순을 지적하더라도 날짜나 문맥의 의미까지 정확히 판별하는 것은 아직 보장하지 못한다.
- 채택된 아이디어가 사소할 수 있으며, 중요도 보정은 미완성이다.
- 계절·요일·준비물 같은 일반 지식 제안은 증거 부족으로 `needs_research`에 남기 쉽다. 기술명도 존재 확인 규칙의 오탐으로 채택이 어려울 수 있다.
- 장소 추천은 적절한 장소 데이터 도구가 없어 품질이 약하다.
- 한국어 문장 패턴에 의존하는 충돌·고유명사 탐지는 오탐과 미탐 가능성이 있다. 의역된 반복 반박도 완전히 잡지 못한다.
- Research가 필요한 도구를 한 번에 모두 요청하지 않아, 관련 증거가 다음 라운드에 늦게 도착할 수 있다.
- 이벤트 기반 자율 시작, 장시간 운영, 일일 예산 소진, 승인 큐의 실제 사용은 아직 충분히 검증하지 못했다.

## 7. 이후 평가 계획

1. 실제 LLM 실행에서 합의·정체 종료를 반복 검증한다.
2. 다양한 주제와 여러 시드로 Research 선택, Critic 품질, 증거-결론 일관성을 측정한다.
3. 채택 아이디어의 유용성·중요도·정확도를 사람 검토와 함께 평가한다.
4. 장소·일정 등 외부 정보의 신뢰도 높은 도구를 보강한다.
5. 충돌·고유명사·반복 판정의 한국어 규칙을 실제 실패 사례로 계속 보정한다.
6. 승인 기반 행동과 장기 운영을 작은 범위에서 검증한 뒤, GYUVIS의 선제 제안으로 점진적으로 연결한다.

## 8. 현재 판단

GyuNexus는 “자율 멀티에이전트 토론이 가능한 MVP”까지는 구현되고 핵심 안전 규칙도 강화된 상태다. 다만 현재의 성과는 **기능 구현과 제한된 검증**이며, 높은 품질의 자율 협업이 일반적으로 보장된다는 뜻은 아니다.

다음 단계의 기준은 기능을 더 붙이는 것보다, 증거를 잃지 않고 서로의 의견을 실질적으로 개선하며 사용자에게 가치 있는 제안만 전달하는지를 반복적으로 평가하는 것이다.
